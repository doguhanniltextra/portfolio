What is a Container? Understanding Linux Kernel Isolation from Scratch

Linux Kernel Containers Docker Go Operating Systems Cgroups

In early August, while researching books to deepen my understanding of a topic where I felt lacking, I stumbled upon a book quite by chance. What began as a book I thought I’d simply skim through quickly ended up prompting brand-new questions right from the early chapters. Far from just finding the answers, actually building those answers took me almost an entire month.

The book is titled Operating Systems: Three Easy Pieces, written by Remzi Arpaci-Dusseau and Andrea Arpaci-Dusseau.

To briefly touch on the book, it thoroughly explains the three pillars of an operating system: Virtualization, Concurrency, Persistence, along with I/O operations which can be considered a fourth pillar tucked in between. Although technical in nature, it is written with an engaging and witty tone. By avoiding academic abstraction and constantly referencing real-world industry applications, the concepts stick with you much better, and I highly recommend reading it.

I don't know about you, but whenever I use a tool, I'm the kind of person who loves looking under the hood. A "take it, use it, move on" mindset has never been an approach I enjoyed. Because of this, I always try to inspect the tools I work with or those widely adopted in the industry, taking notes on their inner workings. Whenever I'm between projects, I look back at these notes to extract new project ideas.

While reading the chapters on Virtualization, I realized that a question I had set aside and never found time for was gradually being answered:

How does Docker provide isolation for its resources on Linux?

To be frank, at first I thought this was a proprietary mechanism unique to Docker. But as the book dug deeper into the topic, I realized that what Docker actually does is orchestrate a few fundamental mechanisms already provided by the Linux kernel. Naturally, that spawned another question:

So, how does Linux actually do this?

That was precisely the question I chased for an entire month. In this article, I want to share what that one-month journey taught me and what I experienced through the small project I built.

Clarifying the Scope

Before diving into what I learned, I feel the need to clarify what a few terms mean in the context of this project so we're on the same page and avoid confusion.

  • When we say virtualization, what are we talking about? Do we mean a Virtual Machine?

Not quite.

When most of us hear the word virtualization, a Virtual Machine (VM) comes to mind. That is completely natural; a VM presents the processor, memory, storage, and other peripherals of a physical machine virtually to another operating system. However, the architecture I explored in this project is different.

With containers, we are not running a brand new operating system. Nor are we spawning a new kernel. Instead, we are providing processes that share the same Linux kernel (we'll get into what a process really is in a moment) with an isolated operating environment.

Therefore, when we say "virtualization" here, we are not referring to hardware virtualization at the VM level, but operating-system-level isolation and virtualization.

About the Project

I built this project from scratch using Golang (1.22+), without touching Docker, runc, or any external container libraries, relying solely on raw Linux kernel syscalls and primitives. My goal was not to build a "production-ready" tool, but rather to truly understand Docker and experience first-hand the foundational mechanisms offered by the operating system.

Where Everything Begins: The Process

The first concept emphasized heavily by the authors of OSTEP was the Process. In daily life, many of us use "program", "application", and "process" interchangeably. But through the eyes of the kernel, there is a vital distinction:

An ".exe" or compiled Go binary sitting on your disk is essentially dead. It is merely a collection of machine code and instructions. When you type ./application into your terminal, the kernel takes these bytes, loads them into memory (RAM), allocates an execution workspace, and tells the CPU: "Now run this."

This living state of dead code brought into memory, consuming resources and running instructions, is what we call a "process".

The metaphor used in OSTEP for this is that the operating system is a master illusionist. When a process runs, the operating system orchestrates such an illusion that it feels as though the entire CPU spins exclusively for it, and the entirety of the 16 GB RAM is dedicated solely to that process.

Towards the end of the virtualization section, during a Q&A between student and teacher, it's quite natural for the student to ask: "...so the operating system is essentially something that acts paranoid?" Because in an environment where thousands of processes share the exact same hardware simultaneously, the kernel cannot trust anyone. A rogue process might enter an infinite loop and lock up the CPU, or another might try to read or overwrite its neighbor's memory. Hence, the kernel is both a grand illusionist and an iron-fisted warden: while making every process feel like it owns its own universe, it keeps a tight grip on their throats, enforcing strict boundaries.

In a standard Linux system, no matter how paranoid the operating system acts, it does not completely conceal processes from each other. When you open a terminal and run an ordinary program today, that program knows full well it is not alone on the machine:

  • When running ps aux, it can see hundreds of other processes running on the host.
  • It can access all files and libraries starting from the root directory (/).
  • It shares the machine's single IP address and network interface with every other application, carrying the risk of consuming arbitrary amounts of memory and freezing the system.

What if we want to take this illusion a step further? What if we blindfold a process so effectively that:

  • It believes it is the sole running process in the entire machine.
  • Instead of seeing the host's actual files, it believes a tiny directory we expose is the whole world.
  • It has its own independent virtual network interface and IP address.
  • No matter how hard it tries, it has iron shackles preventing it from consuming more than 100 MB of RAM.

When you put these special blindfolds on a Linux process and chain its feet with these shackles, the resulting construct is what the industry calls a Container.

The Illusion's Lenses

If what distinguishes a container from an ordinary process is the world it perceives, the lens filtering that world in Linux is called a Namespace.

In the Linux kernel, there are inherently global resources: all process IDs across the system, network interfaces, disk mount points, the hostname...

Normally, every process looks into this shared pool. But the kernel tells us: "If you want, when launching a new process, I can open dedicated windows for it. When looking through that window, it will only see the world I permit it to see."

In the project, I started precisely by putting on these lenses:

1. PID Namespace

In Linux, every process has an identifier (PID). When the machine boots up, the kernel launches systemd (or the init system) as PID 1, and everything else branches out as its descendants.

In the Go code, when spawning the process, I set Cloneflags: syscall.CLONE_NEWPID, and the kernel opens a brand new counter starting from scratch for this process.

Looking from the host machine, this process might be PID 9452, but if you step inside the container and run echo $$, it is now PID 1.

This process now sits at the pinnacle of its own universe; even if it makes a mistake inside and runs kill -9 1, it merely terminates its own world and can never touch the host's real systemd.

The Process Can Still See the Host!

When you create the process, yes, it may appear as PID 1, but if you run ps aux, hundreds of processes running on the host are still visible. The reason behind this lies in the design philosophy of the operating system.

In Linux, the ps command doesn't query the kernel with some magical question. Because everything in Linux is a file, the ps command simply reads a special pseudo-filesystem called /proc and lists the directories inside (where each directory name corresponds to a PID).

So while we blindfolded the process, its feet were still standing firmly in the host's /proc directory, allowing it to see external processes.

To take this a step further, we must provide the process with its own mount table. We need it to forget the host's /proc and mount a fresh /proc from within the container that exposes only the processes visible to itself. This is achieved via CLONE_NEWNS (Mount Namespace).

From here on, things become more familiar. While the UTS Namespace (CLONE_NEWUTS) grants the process the ability to have its own hostname, the NET Namespace (CLONE_NEWNET) places a completely blank routing and interface table before the process. We stripped away the host's ethernet and Wi-Fi adapters, leaving it alone with only an empty loopback (lo) interface.

The Illusion's Shackles

We equipped the process with lenses; it now believes it is PID 1, has zero awareness of the host's other processes, and possesses its own hostname.

Did that solve all our problems? No.

Because even if the process cannot see the outside world, it is still running on the physical hardware of the host machine. If a malicious or careless developer inside this container were to execute the infamous Fork Bomb, the container wouldn't care about isolation; it would saturate the Linux kernel's entire process table, freezing your host machine until you pull the plug. Or if you're lucky, a memory leak would devour your host's RAM, triggering the infamous OOM Killer gun to start arbitrarily shooting down innocent processes on the host just to catch its breath.

To enforce resource limitations, I utilized Cgroups (Control Groups), specifically Cgroups v2.

Managing the Operating System via Cgroups and the Filesystem

The best part about Cgroups v2 is its API. You don't need to invoke any obscure, complex syscalls. Linux's "everything is a file" philosophy saved the day here as well, and I created a container-specific directory under /sys/fs/cgroup/: /sys/fs/cgroup/minicontainer-123/.

Inside this folder, the kernel automatically exposes a set of control files. You simply write limits as plain text into those files:

  • Writing 20 into the pids.max file inside that directory and adding the process PID to cgroup.procs ensures that if someone attempts a fork bomb inside the container, the moment it hits the 20th process, the kernel returns fork: Resource temporarily unavailable, suffocating the attack instantly.
  • With memory.max, you can enforce a strict 100 MB memory cap.
  • With cpu.max, you can enforce hard CPU throttling quotas.

We blindfolded the process and shackled its feet, but there was still another problem: when executing cd / followed by ls inside the container, what we saw was still the host machine's actual disk. I probably don't need to explain how catastrophic that is for a process we intend to isolate.

Filesystem Isolation

We tricked the process regarding its PID and restricted its resources with Cgroups. But a critical vulnerability still remained:

Entering the process and executing cd /home allowed us to view all the files and personal data of the host machine. A container having access to the host's filesystem is an unacceptable security flaw.

We need to tell the container: "Your entire universe consists only of this single folder."

chroot vs pivot_root

When changing the root directory of a process in Linux comes to mind, the classic tool that immediately surfaces is chroot. It has been part of the Unix world since 1979, and frankly, I initially thought about simply using chroot and moving on. However, as I researched further, I was not convinced it was secure enough compared to pivot_root for container isolation. chroot only restricts the current view of the process; a clever process running as root can easily escape using a classic jailbreak trick and crawl back up the hierarchy.

Therefore, just as the modern container ecosystem does, I opted for a much stricter, irreversible syscall: pivot_root.

pivot_root performs what can only be described as architectural gymnastics:

  • First, you place the filesystem of a minimal operating system like Alpine Linux into a directory (assets/rootfs).
  • Using the pivot_root call, you make this directory the new root filesystem of the system.
  • You push the old, genuine root filesystem of the host into a temporary mount location: .old_root.
  • Immediately afterward, you unmount .old_root and detach it entirely from the system.

Once those bridges are burned behind, even if the container executes cd .., reaching the host's files becomes impossible.

Preserving the Base Image: OverlayFS and Copy-on-Write

We isolated the filesystem, but this immediately introduced a practical dilemma:

We only have a single Alpine Linux directory (assets/rootfs). What happens if a user inside the container accidentally deletes or modifies a file? Will our base image be corrupted? Or what if we want to run 3 containers concurrently, will they overwrite each other's files?

Duplicating the disk from scratch for each container would be prohibitively slow and an egregious waste of storage. The mechanism Docker employs to solve this is OverlayFS, and that is precisely what I implemented in the project.

OverlayFS transparently stacks two different directories on top of each other, presenting them as a single unified directory:

  1. lowerdir (Lower Layer): Our original Alpine Linux files. This layer is strictly read-only. The container can never write directly to it.
  2. upperdir (Upper Layer): An initially empty, writable workspace allocated specifically for that container instance.
  3. merged (Unified View): The composite mount point that the container actually enters via pivot_root.

Its operating logic relies on the Copy-on-Write (CoW) principle:

  • When the container reads a file, it reads directly from the lower layer (lowerdir).
  • When the container attempts to modify or delete a file, the kernel immediately copies that file into the upper layer (upperdir) and performs the mutation there.
  • Even if someone runs rm -rf /bin inside the container, the original files remain completely untouched! The kernel simply creates a special marker (whiteout) in the upper layer indicating that the file is deleted.

When the container shuts down, all we have to do is delete that container's specific upperdir directory. Our base image remains pristine, just like day one!

An Overly Isolated Process

Now, our problem wasn't isolating a process, but rather dealing with an overly isolated process. Because we severed all ties to the outside world, it had zero access to the internet.

Remember that we gave the container a fresh NET namespace via the CLONE_NEWNET flag. Consequently, running ip addr inside the container only reveals lo (127.0.0.1). It has neither an assigned IP address nor an ethernet interface to reach the internet.

So how does Docker allocate an independent IP address to each container, and how do containers successfully ping Google?

To solve this problem, I utilized three fundamental networking mechanisms of the Linux kernel:

The Virtual Ethernet Cable: Veth Pair

The Linux kernel features a fantastic construct called veth (virtual ethernet). Think of it as a virtual, bidirectional ethernet cable: any packet you send into one end instantly emerges from the other.

Our code generates a veth pair with two endpoints in the background:

  • One end remains on the host side.
  • The other end is injected directly into the container's isolated NET namespace via a Netlink call.

We rename the endpoint pushed inside the container to a standardized convention (e.g., eth0). Then, we dynamically assign a local IP from our IPAM module to this eth0 interface and bring it up.

The Virtual Switch

We plugged one end of the cable into the container. But where does the end residing on the host connect?

On the host machine, we create a virtual bridge (Linux Bridge) named mc-br0. You can visualize the bridge as a physical network switch sitting in your room.

We attach the host-side cable endpoint (mc-h-xxx) to this mc-br0 bridge and configure 172.19.0.1 as the gateway IP for the bridge. We then instruct the container: "For any packet you wish to send out to the world, your default gateway is 172.19.0.1."

Internet Outbound: IP Forwarding and iptables NAT

When you send a packet from the container to 8.8.8.8 (Google DNS), the packet reaches the host machine. However, the source IP on that packet says 172.19.0.2.

No router on the public internet recognizes this private IP, and none can route the reply back.

This is where two crucial Linux configurations come into play:

  1. IP Forwarding: We tell the kernel by writing 1 into /proc/sys/net/ipv4/ip_forward: "Do not hesitate to forward network packets between interfaces."
  2. NAT (MASQUERADE): We configure an iptables rule on the host: 
    iptables -t nat -A POSTROUTING -s 172.19.0.0/16 ! -o mc-br0 -j MASQUERADE

This rule translates to: Strip the 172.19.0.2 label off every outbound packet leaving the container for the internet, and substitute it with the host's real IP address. When a response arrives from the outside, relay the packet back to the container.

In this manner, the container can communicate with the external world in a controlled fashion using the host's internet connectivity.

Once I translated this entire networking configuration into code and ran the test from inside the container, the result was: 

/ # ping -c 2 8.8.8.8
64 bytes from 8.8.8.8: seq=0 ttl=115 time=12.4 ms
64 bytes from 8.8.8.8: seq=1 ttl=115 time=12.1 ms

Packets were successfully traveling back and forth. A process that started out completely isolated from the host network could now reliably access the internet through its own virtual interface and assigned IP address.

What is a Container, Really?

Let's return to the question I set out to answer at the beginning: So, how does Linux actually do this?

What I realized at the end of this one-month journey is that massive container technologies are simply the orchestration of four core pillars (and, of course, hundreds of clever algorithms): Namespaces, Cgroups, pivot_root, and Veth & NAT.

The creators of Docker are not magicians; they are brilliant engineers who packaged these powerful mechanisms, which the kernel has offered for decades, behind a single, convenient docker run command for all of us.

Final Thoughts

Instead of a "take it, use it, move on" approach, popping open the hood of the tools we use daily might seem daunting at first, but it is one of the most rewarding ways for a software engineer to broaden their horizons. The spark ignited by OSTEP demonstrated to me that the operating system is not an impenetrable black box, but an extraordinary chain of logic operating under precise rules.

TCP'den HTTP'ye: Bir Veri Paketinin Yolculuğu

TCP HTTP Networking Backend Go

Hepimiz öyle ya da böyle bir şekilde REST API kullanıyoruz. Yüzeyde REST API yazsa da altında yatan teknoloji yadsınamaz bir şekilde TCP/IP. Bir butona tıklıyoruz, yarım saniye sonra ekranda veri beliriyor ancak o yarım saniyede tam olarak neler olduğunu hiç düşündünüz mü?

Cihazınızda çalışan işletim sistemi, kullandığınız tarayıcı, aradaki NAT, load balancer, load balancer'a ulaşana kadar araya giren router, switch, firewall ve son olarak sunucu, tüm bunları haberleştiren network katmanları... Bunların her biri kendi içinde karmaşık sistemler barındırıyor ancak ben bu yazıda sadece TCP ve HTTP katmanlarına odaklanacağım çünkü bunların üstüne çoğu zaman fazla düşünmüyoruz.

Hiyerarşik bir şekilde TCP'den HTTP'ye bu veri akışının nasıl gerçekleştiğini, her bir katmanda neler olduğunu ve bu katmanların nasıl bir araya geldiğini ele alacağız.

TCP/IP Modeli - Tam Olarak Neredeyiz?

Öncelikle TCP ve HTTP'ye geçmeden, TCP/IP modeli ile bu iki katmanın nerede bulunduğunu anlamamız gerekiyor. Bunu anlamadan aslında halihazırda soyut olan bir şeyi daha da soyutlaştırıp iyice kafaları karıştırabiliriz. Gelin bu katmanlara bir göz atalım.

Hepimiz OSI modelini duymuşuzdur ancak TCP/IP modeli OSI'nin pratik bir karşılığıdır. OSI 7 katmandan oluşurken, TCP/IP 4 katmandan oluşur.

OSI Modeli (7 Katman)

1- Physical Layer
2- Data Link Layer
3- Network Layer
4- Transport Layer
5- Session Layer
6- Presentation Layer
7- Application Layer

TCP/IP Modeli (4 Katman)

1- Network Access Layer
2- Internet Layer
3- Transport Layer
4- Application Layer

Bu yazıda yalnızca Transport ve Application katmanlarına odaklanacağız; Network Access ve Internet katmanlarını kapsam dışında bırakıyoruz.

TCP/IP modelinde Application kısmında HTTP ve DNS gibi protokoller yer alır. Bu katman aslında OSI'deki 5, 6, 7. katmanların birleşiminden oluşur.

Aynı şekilde TCP/IP modelinde Transport katmanı, OSI'deki Transport katmanının karşılığıdır ve burada TCP ve UDP gibi protokoller yer alır.

Not: Aslında HTTP'yi anlamak için TCP'yi, TCP'yi anlamak için IP'yi, IP'yi anlamak için Ethernet'i anlamamız gerekiyor. Genellikle bizler bu katmanların üstünde soyutlama katmanları oluşturuyoruz. Bu yazıda TCP/IP modelini referans alacağız; gerektiğinde OSI modeliyle karşılıklarına da değineceğiz.

TCP: Transport Katmanı

En baştan özeti vermek gerekirse, TCP, iki endpoint arasında connection kurup byte'ları güvenilir, sıralı ve kontrollü şekilde taşıyan bir transport-layer protokolüdür.

Bu özet üzerinden gitmek istiyorum, burada TCP üzerinde bazı iddialar var; güvenilir, sıralı ve kontrollü.

Bu kavramlar tam olarak neye işaret ediyor? Bunu anlamak için aslında TCP'nin nasıl iletişime geçtiğini, üç yollu el sıkışmayı (three-way handshake) ve segmentları anlamamız gerekiyor. Ardından, verinin güvenli bir şekilde teslim edilip edilmediğini anlamak için acknowledge'ları, timeout'u ve overflow kontrolünü, verinin sıralı teslim edilmesini sağlamak için sequence'ları anlamamız gerekiyor. Son olarak da, connection'ın nasıl kurulup sonlandırıldığını, flow control'u, congestion control'u, error control'u anlamış olacağız. Bu sayede TCP'yi oldukça derinlemesine öğrenmiş olacağız. Sonrasında ise HTTP'nin nasıl çalıştığını TCP üzerinden görmüş olacağız.

Not: Biliyorum çok fazla kavram var, ancak bunların hepsini sırayla ele alacağız ve açıkçası beni asıl heyecanlandıran durum ise, bu kadar karmaşık olan teknolojinin milisaniyeler içinde network üzerinde nasıl çalıştığı.

TCP: Bağlantı Kurma - Three-Way Handshake

TCP protokolü connection-oriented bir protokolüdür yani bazı açılardan paranoyak diyebiliriz. Bağlantı kurmadan kör bir şekilde veri göndermeyi kabul etmiyor. İlk önce iletişim kuracağı cihazla bir bağlantı kuruyor, bu bağlantı sırasında bazı parametreleri konuşuyor, sonrasında veriyi gönderiyor. Bu sayede, TCP bağlantısı her iki tarafta da gerçekten var oluyor, veri göndermek için hazırlar ve veri almak için hazırlar.

İletişim kurma aşamasında Three-Way Handshake denilen 3 aşamalı bir süreç gerçekleşiyor:

  1. SYN (Synchronize): İlk olarak, veri göndermek isteyen taraf (client) karşı tarafa (server) bir SYN paketi gönderir. Bu paket, bağlantı kurmak istediğini belirtir.
  2. SYN-ACK (Synchronize-Acknowledge): SYN paketi alan taraf, bağlantıyı kabul eder ve bir SYN-ACK paketi gönderir. Bu paket, bağlantıyı kabul ettiğini ve veriyi almak için hazır olduğunu belirtir.
  3. ACK (Acknowledge): SYN-ACK paketi alan taraf, bağlantıyı kabul eder ve bir ACK paketi gönderir. Bu paket, bağlantıyı kabul ettiğini ve veriyi almak için hazır olduğunu belirtir.

Peki neden isimleri özellikle SYN ve ACK? Aslında bu isimlendirmeler, TCP paketlerinin header'larında yer alan bazı bayraklardan geliyor. Bu bayraklar, paketlerin ne tür bir paket olduğunu belirtiyor.

Bayrak demişken ona da ufak bir girmek istiyorum, her TCP paketi minimum 20 byte'lık bir header içerir. Bu header; port numaraları, sıra numaraları, pencere boyutu ve bayraklar gibi birbirinden farklı alanlar barındırır. Bayraklar bu alanlardan yalnızca biridir.

SYN, SYN-ACK ve ACK Paketlerinin İçeriği

Öncelikle bu 3 paket türü de TCP paketi olduğu için, 20 byte'lık bir header içerir.

Dipnot: Neden minimum 20 byte? Çünkü sabit alanların toplamı (port numaraları, sequence, acknowledgment, flags, window size, checksum, urgent pointer) 20 byte'a ulaşır. Options alanı eklenirse bu değer artabilir, Payload ise verinin kendisidir.

Bu header'ın içinde port numaraları, sequence ve acknowledge numaraları gibi bilgiler bulunur. Bunlardan detaylı bahsedeceğiz.

TCP header'ının yapısı şöyle:

Field Boyut Açıklama
Source Port 2 bytes Gönderenin port numarası
Destination Port 2 bytes Alıcının port numarası
Sequence Number 4 bytes Gönderenin byte pozisyonu
Acknowledgment Nr 4 bytes Beklenen bir sonraki byte
Header Length 4 bits Header'ın uzunluğu
Flags 9 bits SYN, ACK, FIN, RST...
Window Size 2 bytes Alınabilecek max veri miktarı
Checksum 2 bytes Hata kontrolü
Urgent Pointer 2 bytes Acil veri işaretçisi
Options 0-40 bytes Ek parametreler (isteğe bağlı)
Payload Değişken Asıl veri

Üç paket türü de aynı TCP header yapısını kullanır; farkları yalnızca bazı field'ların değerlerinde yatıyor. Handshake sürecinde asıl önem taşıyan üç alan şunlar: Flags, Sequence Number ve Acknowledgment Number.

SYN SYN-ACK ACK
SYN flag 1 1 0
ACK flag 0 1 1
Seq Number 1000 (client ISN) 5000 (server ISN) 1001
Ack Number 0 (anlamsız) 1001 (ISN+1) 5001 (ISN+1)
Payload Yok Yok Olabilir

TCP Header Alanları Ve Kısa Açıklamaları

Az önce gördüğümüz TCP Header'da birçok parametre var ve bunların her birini detaylı açıklamaktansa akılda kalıcı olması açısından ana başlıklar altında incelemek istiyorum:

  1. Source Port ve Destination Port: Gönderenin ve alıcının port numaralarını belirtir. Port numarası, hangi uygulamanın veriyi alacağını belirtir. Örneğin 80, 8080, 443 portları web tarayıcıları tarafından kullanılırken, 25, 465 portları e-posta uygulamaları tarafından kullanılır.
  2. Sequence Number: Gönderenin başlangıç byte pozisyonudur. Her iki taraf bağlantı başında rastgele bir ISN (Initial Sequence Number) seçer. Bu rastgelelik kasıtlıdır — eski bağlantılardan kalan paketlerin yeni bağlantıyla karışmaması için.
  3. Acknowledgment Number: Beklenen bir sonraki byte'ı belirtir. Her zaman alınan Seq Number + 1 değerini taşır.
  4. Header Length: Header'ın uzunluğunu belirtir. Bu alan 4 bit uzunluğundadır ve 0 ile 15 arasında değer alabilir. Bu değer, header'ın toplam uzunluğunu byte cinsinden ifade eder.
  5. Flags: SYN, ACK, FIN, RST gibi bayrakları içerir. SYN bayrağı "bağlantı başlatmak istiyorum", ACK bayrağı ise "bir önceki paketi aldım" anlamına gelir.
  6. Window Size: Alınabilecek max veri miktarını belirtir. Bu alan, alıcının ne kadar veriyi tek seferde alabileceğini belirtir. Bu değer, alıcının tampon belleğinin (buffer) ne kadar büyük olduğunu gösterir.
  7. Checksum: Hata kontrolü yapar. Bu alan, verinin bütünlüğünü kontrol etmek için kullanılır. Veri üzerinde yapılan matematiksel bir işlem sonucunda elde edilen değerdir.
  8. Urgent Pointer: Acil veri işaretçisi. Bu alan, acil veriyi işaret eder. Bu veri, hemen işlenmelidir.
  9. Options: Ek parametreler (isteğe bağlı). Bu alan, isteğe bağlı parametreleri içerir. Bu parametreler, header'da bulunmayabilir.
  10. Payload: Asıl veri.

TCP: Reliable Delivery - Güvenilir Teslimat

TCP'nin en önemli özelliklerinden biri güvenilir teslimattır. TCP, verinin karşı tarafa hatasız ve sırası bozulmadan ulaşmasını garanti eder. Bu özelliği sağlamak için kullandığı üstteki başlıklarda da bahsettiğim iki önemli mekanizma vardır: Sequence Numbers ve Acknowledgments.

Bunların yanı sıra TCP, Timeout ve Error Control gibi mekanizmaları kullanarak verinin güvenli bir şekilde teslim edilmesini sağlar. Bunları da detaylıca işleyeceğiz.

Somutlaştırmak adına bir senaryo inceleyelim:

Senaryo: Diyelim ki 3000 byte'lık bir veri gönderiyorsun. TCP bunu 3 ayrı segmente böldü: 1000, 1001-2000, 2001-3000. İkinci segment kayboldu. Bu durumda ne olacak?

Segment yani paketler, soruda da görüldüğü gibi parçalanma durumunda sıra numaraları sayesinde birleştirilirler. ACK mekanizması ise paketlerin karşı tarafa ulaşıp ulaşmadığını kontrol etmek için kullanılır. Timeout + Retransmission mekanizması sayesinde ise kaybolan paketler tekrar gönderilir.

Peki aynı soruyu genişletirsek ve Server tarafı "Benim buffer'ım doldu, artık doydum yavaşlaman gerek" derse ne olacak? İşte burada Window Size devreye giriyor.

Window Size, alıcının ne kadar veriyi tek seferde alabileceğini belirtir. Bu değer, alıcının tampon belleğinin (buffer) ne kadar büyük olduğunu gösterir. Gönderici, Window Size'ı aşmadan veri gönderir.

Bu yapıyı daha da somutlaştırırsak veri gönderimi hiyerarşik olarak şu şekilde olur:

1. Başrol Oyuncuları: Server ve Client

Client 3000 byte'lık bir veri göndermek istiyor. Three-way handshake tamamlandı, bağlantı kuruldu. Server ise dinliyor, Receive buffer boyutu = 4000 byte (Window Size = 4000). İkisi de gayet hazır gözüküyor.

2. Asıl Show Başlıyor: Veri Gönderimi (Data Transfer)

Başarılı Three-way handshake sonrası Client 1000 byte'lık veri gönderir. Server, bu 1000 byte'ı alır, Receive buffer'da saklar ve bir ACK paketi gönderir. ACK, 1001. byte'ı beklediğini belirtir. Client, Server'dan ACK alır almaz 2000 byte'lık bir veri daha gönderir. Server, 2000 byte'ı alır, buffer'da birleştirir ve 3001. byte'ı beklediğini belirten bir ACK gönderir. Client, son 1000 byte'ı gönderir. Server, 1001., 2001. ve 3001. byte'ları sırasıyla buffer'a ekleyip 4001. byte'ı beklediğini bildirir.

3. Peki Ya Bir Paket Kaybolursa?

Senaryomuzda Client 2000 byte'lık ikinci segmenti gönderdiğinde paket kayboldu. Server, 2001. byte'ı beklemeye devam eder ancak bu segment hiç ulaşmaz. Client tarafında ise belirli bir süre ACK gelmez, bu süre dolunca timeout yaşanır ve Client kayıp segmenti tekrar gönderir. Bu mekanizma veri kaybını önler ve güvenilir teslimatı sağlar.

4. Peki Ya Server'ın Buffer'ı Dolarsa?

Buffer dolarsa, Server yeni veri kabul etmez ve Window Size 0 olur. Bu durumda Client veriyi göndermeyi bırakır ve Server'dan gelen ACK'ları bekler. ACK gelmeye başlayınca Window Size artar ve veri akışı devam eder.

TCP: Connection Termination - Bağlantı Sonlandırma

Yazının en başında söylediğim gibi TCP biraz paranoyak bir hale sahiptir, evden çıkarken kapıyı kilitler, geri dönüp "Acaba kilitledim mi?" diye kontrol eder, sonra tekrar çıkar. Bağlantı sonlandırma aşaması da bu paranoyanın bir sonucudur. Aslında mantıklı bir şüphedir, çünkü veri paketleri internet üzerinde kaybolabildiği gibi, aynı zamanda bağlantı da kopabilir. Bu nedenle, bağlantı sonlandırma aşaması da oldukça detaylı ve dikkatli bir şekilde gerçekleştirilir.

Bu süreçte FIN ve ACK paketleri kullanılır. FIN bayrağı "artık veri göndermeyeceğim, bağlantıyı kapatmak istiyorum" anlamına gelir. ACK bayrağı ise karşı tarafın FIN'ini aldığını onaylar. Her iki taraf da kendi FIN'ini gönderip karşılıklı ACK aldığında bağlantı tamamen sonlandırılır.

HTTP: Application Layer

TCP'yi tanıdıktan sonra HTTP'nin ne olduğunu ve nasıl çalıştığını anlamak daha kolay olacaktır. HTTP, TCP'nin üzerine kurulu bir protokoldür. TCP, veriyi taşırken, HTTP verinin ne olduğunu belirtir. Bu ikisi birlikte çalışarak güvenli ve düzenli veri transferi sağlarlar.

HTTP'yi en iyi bir sözleşme olarak düşünebiliriz. TCP byte'ları taşır ancak bu byte'ların ne anlama geldiği sorusuna cevap vermez. HTTP ise bu soruyu cevaplar: Client ne istiyor, server ne döndürüyor?

HTTP, her zaman bir istek-cevap çiftinden oluşur. Client bir Request gönderirken Server da bir Response döner. Bu döngü, bağlantı kapatılana kadar devam eder.

HTTP'nin Request yapısı ise:

GET /index.html HTTP/1.1
Host: example.com
Accept: text/html
User-Agent: Mozilla/5.0

HTTP'nin Response yapısı ise:

HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 1234

<html>...</html>

Tıpkı bir mektup gibi: önce ne istediğini yazar, sonra ne tür bir içerik beklediğini belirtirsin ve en sonda asıl mesajını eklersin. Headers ile body arasındaki o boş satır küçük ama kritik, HTTP'de bu satır olmadan nerede header'ın bittiği, nerede body'nin başladığı bilinmez.

HTTP/1.0'da her request-response döngüsü bağlantıyı kapatırdı, yani her istek için yeni bir TCP three-way handshake gerekiyordu. HTTP/1.1 bu sorunu Connection: Keep-Alive header'ı ile çözdü ve aynı TCP bağlantısı üzerinden birden fazla istek gönderilebilir hale geldi.

Peki TCP ile birleştiği yer tam olarak neresi?

Bu HTTP mesajları aslında TCP'nin Payload kısmına yerleştirilir. Yani TCP, HTTP'nin Application Layer protokolünü taşır. Bu şekilde, HTTP, TCP'nin güvenilir teslimatından faydalanır ve verinin karşı tarafa hatasız ve sırası bozulmadan ulaşmasını sağlar. Bu sayede bizler de güvenli bir şekilde internet üzerinde gezinir, e-posta göndeririz.

TCP'ten HTTP'ye: Büyük Resim

İşte bu iki protokolün bir araya gelmesiyle internet üzerinde nasıl güvenli ve düzenli bir veri transferi sağlandığını özetlemek gerekirse:

1. Bağlantı İsteği

Tarayıcı adres çubuğuna example.com yazıp Enter'a basıyorsun. Tarayıcı, example.com'un IP adresini DNS üzerinden öğreniyor ve 80 numaralı porta TCP bağlantısı açmak istiyor. Henüz HTTP'den haber yok; sahne TCP'ye ait.

2. Three-Way Handshake

Tarayıcı  ──SYN──────────────────►  Sunucu
Tarayıcı  ◄──────────SYN-ACK──────  Sunucu
Tarayıcı  ──ACK──────────────────►  Sunucu

Her iki taraf ISN'lerini paylaştı ve pencere boyutlarını belirledi. Bağlantı kuruldu. TCP işini yaptı, şimdi sıra HTTP'de.

3. HTTP Request TCP Payload'ına Giriyor

Tarayıcı bir HTTP isteği oluşturuyor:

GET /index.html HTTP/1.1
Host: example.com
Accept: text/html
User-Agent: Mozilla/5.0

Bu metin, bir TCP segmentinin Payload alanına yazılıyor ve sunucuya iletiliyor. TCP bu verinin bir HTTP isteği olduğunu bilmiyor; onu byte dizisi olarak taşıyor, ACK alıyor ve işi bitiyor.

4. Sunucu İşliyor ve HTTP Response Gönderiyor

Sunucu TCP segmentini alıyor, Payload'dan HTTP isteğini çıkarıyor ve işliyor. Ardından kendi HTTP yanıtını oluşturuyor:

HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 1234

<html>...</html>

Bu yanıt da yine TCP segmentinin Payload'ına yerleştiriliyor ve tarayıcıya gönderiliyor. TCP katmanı sıralamayı ve bütünlüğü garanti ediyor; HTTP katmanı ise gelen byte'ları parse edip sayfayı render ediyor.

5. Bağlantı Kapanıyor (ya da Açık Kalıyor)

HTTP/1.1 ile birlikte Connection: Keep-Alive varsayılan olarak aktif olduğundan aynı TCP bağlantısı üzerinden başka istekler de gönderilebilir. İşler bitince four-way handshake ile bağlantı nazikçe kapatılıyor.

Sonuç: Ekrana yansıyan o sayfa, milyonlarca kez tekrar eden bu döngünün sonucudur. TCP kurar, HTTP konuşur, TCP kapatır. Ve sen hiçbirini fark etmezsin.

Raw TCP ile HTTP İsteği Göndermek - Pratik

Bu kadar uzun teorik yazıdan sonra ufak bir kod kısmı koymak istedim. Golang dilini kullanarak raw bir TCP bağlantısı kurup, HTTP isteği göndereceğiz. Ardından da response'u alacağız. 

package main

import (
	"fmt"
	"io"
	"net"
)

func main() {
	conn, err := net.DialTimeout("tcp", "google.com:80", 5*time.Second)
	if err != nil {
		fmt.Println("Hata:", err)
		return
	}
	defer conn.Close()

	// HTTP Request
	request := "GET / HTTP/1.1\r\nHost: google.com\r\nConnection: close\r\n\r\n"
	_, err = conn.Write([]byte(request))
	if err != nil {
		fmt.Println("Hata:", err)
		return
	}

	// Response okuma
	body, err := io.ReadAll(conn)
	if err != nil {
		fmt.Println("Hata:", err)
		return
	}

	fmt.Println(string(body))
}

Run: go run main.go

Google'a HTTP/1.1 ile istek attığımızda ne gelir? Google, HTTP isteklerini HTTPS'e yönlendirdiği için 301 Moved Permanently yanıtı döner: 

HTTP/1.1 301 Moved Permanently
Location: https://www.google.com/
Content-Type: text/html; charset=UTF-8
Content-Length: 220
Date: ...

<HTML><HEAD><meta http-equiv="content-type" ...>
<TITLE>301 Moved</TITLE></HEAD>...

Bu tam olarak beklenen davranış. Google sana "Ben artık HTTPS'teyim, 80 portuna gelme" diyor.

Peki aynı şeyi net/http ile yapsaydık:

package main

import (
	"fmt"
	"io"
	"net/http"
)

func main() {
	resp, err := http.Get("http://google.com")
	if err != nil {
		fmt.Println("Hata:", err)
		return
	}
	defer resp.Body.Close()

	body, _ := io.ReadAll(resp.Body)
	fmt.Println(resp.Status)
	fmt.Println(string(body))
}

Daha kısa, daha temiz. Ama arka planda aynı şey oluyor: TCP bağlantısı açılıyor, HTTP metni Payload'a yazılıyor, response okunuyor. net/http bunu senin için gizliyor; raw TCP versiyonu ise her adımı göz önüne seriyor.

Çıkarım: İşte bu yazıda anlatmak istediğim şey tam olarak buydu. REST API çağırırken aslında ne yaptığını bilmek, bizi daha iyi bir yazılımcı yapacağına inanıyorum.

Bir Adım Ötesi: HTTPS

TCP, veriyi güvenilir biçimde taşır; kayıp olmaz, sıra bozulmaz. Ancak şifrelemez. Yani ağı dinleyen biri TCP segmentlerini yakalasa, içindeki HTTP metnini düz olarak okuyabilir.

Bu sorunu çözmek için HTTPS devreye girer. HTTPS aslında HTTP değil, HTTP + TLS (Transport Layer Security) demektir. TLS, TCP ile HTTP arasına oturur. TCP bağlantısı kurulduktan sonra bir TLS handshake yapılır ve bundan itibaren tüm HTTP mesajları şifrelenmiş olarak taşınır. Yani TCP byte taşımaya devam eder, ama bu sefer byte'lar şifreli gelir.
